# RazorBlazorDataExchange 0.6 — Ordered delivery and transport abstraction

Version 0.6 is an additive evolution of the 0.5 singleton broker. It does **not** change the core communication invariant:

- the application broker remains a singleton;
- `SessionId` is only an isolation boundary;
- Razor/MVC and Blazor remain symmetric publishers/subscribers;
- communication remains valid across multiple Blazor Server/SignalR circuits in the same session;
- the existing `Publish`, `PublishAsync`, `Update`, `UpdateAsync`, `Subscribe` and `SubscribeSession` APIs keep their 0.5 behavior.

## Ordered exchange facade

`RazorBlazorOrderedDataExchange` is an optional singleton facade registered together with the core broker.

Use it only when a workflow requires completion ordering. Direct calls to `RazorBlazorDataExchange` remain unchanged and are not forced through an ordering queue.

```csharp
var message = await orderedExchange.UpdateAsync<int>(
    sessionId,
    "Counter",
    current => current + 1,
    actorId);
```

Two ordering granularities are available.

### `SessionAndProperty`

This is the default. Operations for the same `(SessionId, PropertyName)` are serialized until all asynchronous subscribers of the current publication have completed. Different properties and different sessions can progress concurrently.

```csharp
await orderedExchange.PublishAsync(
    sessionId,
    "Status",
    "ready",
    actorId,
    orderingScope: RazorBlazorExchangeOrderingScope.SessionAndProperty);
```

### `Session`

All ordered operations in one session share a single lane, even when they target different properties. This is appropriate for workflows in which notifications cascade across multiple related properties and the application needs a single session-level completion order.

```csharp
await orderedExchange.PublishAsync(
    sessionId,
    "Status",
    "ready",
    actorId,
    orderingScope: RazorBlazorExchangeOrderingScope.Session);
```

## Reentrant publications

A subscriber can publish again while the outer ordered publication is still awaiting its subscribers. Re-acquiring the same lane would deadlock, so a causally nested publication on an already-held lane executes inside that lane instead of trying to acquire it again.

`RazorBlazorOrderedDataExchangeMetricsSnapshot.ReentrantBypasses` exposes how often this occurs.

This behavior is intentionally limited to nested/reentrant flows. Independent top-level callers still acquire the lane and are ordered normally.

## Lane lifecycle

Ordering lanes are created on demand and reference-counted. When the last active/waiting operation releases a lane, the lane is retired and removed from the internal dictionary. Dynamic session/property names therefore do not create permanently retained semaphore entries.

Metrics exposed by `GetMetrics()` include:

- active lanes;
- entered operations;
- completed operations;
- cancelled operations;
- reentrant bypasses.

## Transport abstraction

`IRazorBlazorDataExchangeTransport` is an infrastructure SPI intended for future multi-process adapters.

The default implementation is:

```text
InMemoryRazorBlazorDataExchangeTransport
```

It performs broadcast fan-out to all registered transport consumers and isolates failures so one broken transport consumer does not prevent delivery to the others.

The default transport is **not** a second broker and does not replace the singleton `RazorBlazorDataExchange` instance.

## Wire envelope

`RazorBlazorTransportEnvelope` deliberately uses transport-safe metadata:

- `OriginNodeId`
- `SessionId`
- `PropertyName`
- `ActorId`
- `MessageId`
- `CorrelationId`
- `SourceVersion`
- `Timestamp`
- `ValueTypeName`
- `PayloadJson`

The payload is JSON and the type is represented by name. The envelope therefore does not carry live CLR object references or a `System.Type` instance across a transport boundary.

An existing typed exchange message can be converted with:

```csharp
var envelope = RazorBlazorTransportEnvelope.FromMessage(
    exchangeMessage,
    originNodeId: "web-node-01");
```

and deserialized with:

```csharp
var value = envelope.DeserializeValue<MyPayload>();
```

## Replacing the transport

The application-facing broker API does not change when a transport adapter is replaced.

```csharp
services
    .AddRazorBlazorDataExchange()
    .UseRazorBlazorDataExchangeTransport<MyRedisTransport>();
```

`MyRedisTransport` only has to implement `IRazorBlazorDataExchangeTransport` and is registered as a singleton.

## Important scale-out boundary

0.6 introduces the transport contract and a serialization-safe envelope, but it **does not claim automatic distributed broker replication yet**.

A true multi-process implementation still needs an ingress/egress coordinator with explicit policies for:

- node-origin filtering;
- message deduplication;
- source vs local version reconciliation;
- reconnect/replay behavior;
- delivery guarantees (at-most-once / at-least-once);
- distributed ordering semantics;
- authentication/authorization of transport messages.

Those policies must be defined before enabling transparent Redis/Service Bus replication. Keeping them outside 0.6 prevents the transport abstraction from silently changing the well-tested 0.5 broker semantics.

## Validation added in 0.6

`RazorBlazorDataExchange.V06Tests` validates:

- completion ordering on the same session/property lane;
- parallel progress of different property lanes;
- session-wide ordering across different properties;
- reentrant same-route publication without deadlock;
- concurrent ordered atomic updates;
- in-memory transport broadcast fan-out;
- transport subscriber failure isolation;
- JSON transport-envelope round-trip;
- default DI registration and custom transport replacement.

The existing 0.5 stress tests and Playwright browser E2E suite remain part of CI, so the new ordering/transport layer is validated without weakening Razor ↔ Blazor or cross-circuit behavior.
